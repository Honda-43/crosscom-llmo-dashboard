立ち上げ期で母数が小さく、**半数の記事を放置するコストが統計的な厳密性に見合わない**。

## 2. 記事単位のGSC(gsc_pages)— 50記事の主指標

### 2-1. タブ定義

| 列 | 内容 |
|---|---|
| `date` | 日付 |
| `page` | 記事URL(`#見出し` は落として同じ記事にまとめる) |
| `impressions` | 表示回数 |
| `clicks` | クリック数 |
| `position` | 平均掲載順位(表示回数で重み付け、小数2桁) |
| `queries` | その日にその記事が表示された**匿名化されていない**クエリの種類数 |

鍵は `date × page`(upsert・再実行で重複しない)。**`gsc_branded` の集計は変更していない。**

### 2-2. 取り方

- impressions / clicks / position は `dimensions=['page','date']` から取る。
  `['page','query','date']` は匿名化クエリが落ちるので、合計に使うと過少になる。
- queries は `['page','query','date']` のクエリ種類数。
- 25,000 行の上限ちょうどで返ったら `startRow` で続きを取る。
- `#見出し` 違いをまとめると、同じ検索結果に両方出た表示は2回に数えられる(GSCの仕様)。
  記事が2行に割れるより害が小さいので、まとめる側を選んだ。

### 2-3. 日次

`run_daily.py` が指名検索と同じ **3日前**(GSC の確定待ち)の1日分を取って書く。
書き込み前に読むのは鍵の2列だけ。

### 2-4. バックフィル(16か月分)

GitHub Actions の `backfill-gsc-pages` で実行する(ローカルは GSC API 無効・シート閲覧者のため不可)。
既定の期間は **16か月前 〜 3日前**。手動で再実行するときは dry_run で件数を見てから書く。

**実行結果:** (§8 に記録)

### 2-5. 50記事と施策の紐づけ(未実装・必要)

`gsc_pages` を主指標にするには、**どの記事にいつ施策を打ったか**が要る。
現状の `action_log` は「対象」がプロンプトID(E-1 など)で、記事URLが残っていない。

- 50記事の一覧(URL)と、記事ごとの実施日を記録する場所が必要。

## 3. 効果の読み方

### 3-0. 前提:同じ面の観測は独立ではない

| 単位 | ICC | 扱い |
|---|---|---|
| 面ごと(同じ面の中の観測) | **0.21** | 面ごとに前後を比べる。観測数をそのまま標本数として数えない |
| 面をまたいだ場合 | **0.57** | **面をまたいで独立扱いしない。** 複数の面を1つの標本に混ぜて件数を増やさない |

同じまとまりの中の観測が似ているほど(ICCが高いほど)、観測数を増やしても情報は増えない。
目安は設計効果 `1 + (1まとまりの観測数 − 1) × ICC` で、実質の標本数は観測数をこれで割った値になる。
**独立として数えると区間が狭く出すぎ、効果があるように見える方向に偏る。**

### 3-1. 面ごとの前後比較(主)

| 項目 | 方針 |
|---|---|
| 面 | 記事(50記事の施策、`gsc_pages`)/プロンプトの面(A-1〜B-3、言及率) |
| 比べるもの | 実施日の**前の同じ長さの期間**と後の期間 |
| 期間 | 記事は実施前後各4週(週単位に集計。日次は0が多すぎる)。言及率は前後各14観測日以上 |
| 効果の大きさ | 記事:クリック・表示回数の**比**(後÷前)と順位の差/言及率:ポイント差 |
| 不確実性 | 面の中の日の相関を考慮した区間(ブロック・ブートストラップ:週単位で再標本化) |
| 集約 | 面ごとの結果を**並べて**見る(何面で上がり、何面で下がったか)。まとめて1つの数字にするときは面を単位にする(面の中央値、または面をクラスタにした推定) |

- 前年同時期の同じ期間の比(16か月のデータがある記事)を並べ、季節性で動く幅の目安にする。
- 記事×日の行を全部つないで1本の回帰にかけ、行数を標本数として扱うことはしない。

### 3-2. 中断時系列分析(主)

| 項目 | 方針 |
|---|---|
| 系列 | 週次:50記事合計のクリック・表示回数(`gsc_pages`)、AI経由セッション、指名検索クリック |
| モデル | 区分回帰:`y = 切片 + 傾き・t + 水準変化・実施後 + 傾き変化・(t − 実施時点)・実施後` |
| 自己相関 | Newey-West 標準誤差(週次の値は前週と相関する) |
| 季節性 | 16か月の過去データから前年同週の動きを確認し、明らかな季節パターンがあれば説明変数に入れる |
| 効果の大きさ | 水準変化・傾き変化を区間つきで出す |

- **実施日をずらしていれば**、施策ごとに中断時点を置ける。同日実施のもの(§4)は1つの中断として扱い、
  個別の効果は出さない。
- AI経由キーイベントは 9/1 より前が欠測のため、実施前の期間が取れず中断時系列にできない。水準の推移のみ見る。
- 正式指標(Salesforce)も 8/24 より前が存在しないため同様。

## 4. 実施日の運用と同日実施の記録

### 4-1. ルール

1. **施策の実施日は原則ずらす。** 同じ日に複数のサイト全体施策を重ねない。
2. やむを得ず同日に実施した場合は、`action_log` に **「同日実施のため個別効果は分離不能」** と記録する。
3. 同日実施の施策は**まとめて1つの介入**として読み、1本ずつの効果を報告しない。

「ずらす」間隔の目安は、読みたい指標が反応するまでの時間。
取り下げURLの引用が消えるまでの実測は 2〜3日(A-011、1事例)。記事の表示・クリックは
GSC の確定に3日かかるので、**最低でも1週間**空けないと前後の区切りが混ざる。

### 4-2. 実装(2026-09-14)

| 項目 | 内容 |
|---|---|
| 列 | `action_log` の**末尾**に `備考` を追加(既存列の並びは不変) |
| 判定 | `実施日` が同じ日付の施策が2本以上ある日(実施日が「—」の行は対象外) |
| 記録 | `同日実施のため個別効果は分離不能(2026-08-24にA-004/A-005と同日)` |
| 実行 | **週次(run_weekly)で自動**。実施日は人がシートで入れるので、毎週読み直して足りない記録だけ書く |
| 手動 | `cd src && python action_log.py --mark-same-day [--dry-run]` |
| 書き方 | 対象セルだけを書く(行ごと上書きしない)。人が書いた備考は消さずに後ろへ足す。記録済みの行は書き直さない |

「サイト全体施策かどうか」はシート上で区別できる列が無いため、**実施日が重なった施策はすべて記録する**。
記事単位の施策同士が同日でも、同じ理由(前後の区切りが混ざる)で分離できない。

2026-09-14 時点の `action_log` で実施日が重なっているのは **2026-08-24 の A-003 / A-004 / A-005**。

## 5. 判断の仕方(p値で合否を決めない)

- **p値で合否を判定しない。** 件数が小さいうちは有意にならないことが「効果が無い」を意味せず、
  観測を増やせば実務上意味のない差でも有意になる。
- 報告するのは **効果の大きさ(点推定)と不確実性の幅(区間)**。
- 判断は **事前に決めた継続判断の閾値** と突き合わせる。

| 判断 | 条件 |
|---|---|
| **継続・横展開** | 点推定が閾値以上で、区間が悪化側に大きくはみ出していない |
| **観測を延長** | 点推定は閾値付近だが区間が広い(データが足りない) |
| **停止・見直し** | 点推定が閾値を明確に下回り、区間の上限も閾値に届かない |

| 対象 | 効果の大きさ | 継続判断の閾値(**初期案・要決定**) |
|---|---|---|
| 50記事(`gsc_pages`) | クリック比(実施後÷実施前、前年同時期の比で補正) | 1.20 以上(+20%)の記事が過半 |
| サイト全体 | AI経由セッションの水準変化(週あたり) | +3セッション/週 |
| LLM言及率 | 面ごとのポイント差 | +10ポイントの面が過半 |

> **閾値の数値は、分析を回す前に決めてこの表を更新する。**
> 結果を見てから決めると後付けになる。数値は「この程度動かなければ工数に見合わない」という
> 事業側の基準で、統計から出る数字ではない。
